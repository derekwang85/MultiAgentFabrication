# 治理优先于调度

> 把 Agent 串起来的调度表再漂亮，也盖不住一个欠账：哪条规矩在派活之前被机器验证过？Multi-Agent 的铁律不是"任务怎么流"，是"没被校验的规矩，不准放它去碰真实请求"。

## 一、最危险的多 Agent，不是 Agent 懒，是调度员太勤

我见过一种越来越普遍的系统病：System prompt 越写越长，Agent 越转越密，日志一层又一层，可你问任何一个人"哪条规矩在真拦、哪条是在表演存在"，没人答得上来。

这不是 Agent 的功能故障，是治理欠了账。任务一路派下去了，每个环节看起来都在干活，可整条链从头到尾没被任何一条"派活前的不变量"关过——规矩是写给文档的，不是写进闸门里的。调度员越是勤快，这个洞越被漂亮的流转掩盖。

我给第八篇立个靶子：**规矩必须先于调度被验证。** Multi-Agent 的生产力来自熵被管理；熵被管理的第一步，不是把任务派得更快，是让不该进花园的东西，进不了花园。

## 二、先立规矩，再派人

把"调度优先"换成"治理优先"，改变的恰恰是派活的顺序。传统的 Agent 编排把注意力全压在"谁调谁、怎么接力"上，仿佛整条链的成败只在这一层的编排质量。可真相是：任务怎么流，解决的是"流得顺不顺"；治理怎么落，才决定"流出去的东西对不对"。

于是我把规矩当成了派活的前置闸门，而不是附在调用那一刻的检查。规约里写死了什么叫合法请求、边界在哪、谁的证据才算数——全部先进门禁被机器验过一轮，验不过的请求，直接堵回去，不进调度层。规矩不是给 Agent 读的提醒，是被编码成可以挡人的闸。

这张闸门长什么样的？它有三道可以逐个落地的关卡：一验"请求是否合法"（来源、影响面、回滚预案是否齐备）；二验"是否越界"（碰没碰受宪章管辖的那类资源）；三验"证据是否有效"（读的参考值是否来自已核实快照）。三道都在调度之前对同一份请求跑，跑完才谈"派给谁"。顺序不能倒：先问"该不该流"，再谈"怎么流"，最后才是"流给谁"。很多编排框架把前两问揉进流程里当参数，就成了前面说过的"权限附在调用时刻"——那不是前置门禁，是故障后的贴身检查。

Multi-Agent 的核心主张 A5 在这里收束成一句：**治理优先于调度 = 先立规矩 × 派活前验收 × 独立账复核。** 调度可以是灵活的，但它的活动半径，必须被先于它成立的规约圈死。

## 三、法不阿贵，绳不挠曲

我把这层道理往哲学锚点上靠，借的是韩非子。"法不阿贵，绳不挠曲"（《韩非子·有度》）——法不偏袒位高的人，墨线不迁就弯的木料。韩非所讲的"以法为尺"，恰恰是 Multi-Agent 要回的那口气：规矩面前，每个 Agent 都该平等，不靠临场求情，不靠当时的调度员心情。

把这句话翻到机器上，就是可验证的确定性。人工评审会照顾脸面，调度器会图省事；只有把规矩编译成可判定的闸，验证人人平等，才谈得上"没有后门、没有特例"。Multi-Agent 敢不敢对证据负责，取决于它的规矩是不是像墨线一样不吃力、不转弯。这里的"编译"二字是字面的：规约要长成能被测试套件逐条打勾的断言，而不是一段"建议遵守"的散文。散文靠 Agent 自觉，断言靠机器执行，韩非讲的"绳不挠曲"，落在工厂里就是那行不许被绕过、不许被求情的 `if not (evidence.origin in trustworthy_snapshots): reject(request)`。

用得诚实一点：韩非的法偏向严控，我不为严控背书，只借他那把"以法为尺"的确定性。多 Agent 要的不是人人自危的紧，是规矩放到派活之前、且看得见摸得着的稳。门槛不越，花园自清。

## 四、后期成本是前期十倍，门禁必须前置

为什么非要先用规矩挡一轮、再放任务去流？因为这个账在工程管理里早就被算过：**后期才发现的问题，修复成本是前期的十倍往上。** 规约在派活前被机器验一次，买的是整个生命周期里最便宜的一份保险。等请求已经流进调度、跑完全链、盖了"产出判定"章，再回头说"这单本来就不该进"，到那时要拆的不只是规则，是已经被污染的那一本账。

Multi-Agent 早期就栽过这个跟头，是"先派活再补规矩"的典型反例 `[内部项目实测]`：一个带"写操作"的高权限 Agent 被直接放进生产链，团队想着"先跑起来、规矩后面补"。结果它一通调度把不该落库的临时判定写进了对外接口，事后补规矩堵住洞时，光回滚那批脏数据就花了三个排期，比一开始就把"写生产需双签"编译进闸门贵了一个量级。

教训不是"别用高权限 Agent"，是**该在闸门这一步就否掉的请求，绝不要让它先流出去再收拾。** Multi-Agent 的门禁目标从来不是"零错误通过"，是让写错比写对更麻烦——顺着转的请求越来越顺，越界请求寸步难行。规矩前置不是流程税，是压在翻车概率上最便宜的一笔保证金。

## 五、一张"派活前不变量"清单

门槛立不立得住，看它能不能落成可判定的字段。我把 Multi-Agent 常用的一条不变量清单抄在下面，每栏都写死、都能被机器验，而不是停在文档里当提醒 `[内部项目实测]`：

- **合法请求**：凡进入调度层的请求，必须带三样——`来源签名`（谁发起的）、`影响面`（会碰哪些模块）、`回滚预案`（挂了怎么退）。缺一样，请求在闸门就被打回，不进调度。
- **边界**：任何请求若触碰生产配置，必须过`双签`；单签视为未获授权，直接拦截。业务 Agent 无权把判定直接落生产。
- **证据**：只有来自"已核实快照"的读数才被当作证据，过期参考值视为无证据，宣称回待审，不许带病上桌。

这清单看着像在立规矩，其实是把"该不该流"从调度员的临场判断里拿了出来，前置成一道机器能读的闸。Multi-Agent 敢给人可证明的承诺，先从让这条清单真的在挡人开始，而不是指着文档说"我们有规矩"。

清单本身也禁不起一个人偷偷改。所以它还要过第三道账——独立账复核：清单本身是"活文档"，但它每次被改，都得在另一份与调度无关的账本里留痕，改的人、改的时点、改的 diff，逐条可回溯。这样"派活前不变量"才不会演变成"某个深夜被悄悄放宽的闸门"。规矩前置解决"该不该流"，独立账解决"这份规矩自己有没有被动手脚"，两者合起来，A5 那句公式才算真的闭合成一条能让人放心的链。

把这张清单放回第十三篇立起的双层结构里看，它的归属立刻清楚了 `[内部项目实测]`：**这张"派活前不变量"不是调度层自己在现场拍脑袋定的，它是元层作为一件产物，编译好了下发给产品层去执行的。** 在我的内部项目里，宪章、红线、双签口径这些规矩，都长在元层的规则库里——元层造系统的时候，一本正经地把它当零件一样编译、验收、留痕，再下发到产品层；产品层的转发器只在派活的瞬间读这份已经过检的账，严格说它根本没有权限现场改动这些规矩，能动的只有"这份规矩引用的是不是最新版本库"。把两层分开后，"先立规矩再派人"就有了一个更硬的落点：规矩不是某个调度员的临时偏好，而是元层交付物的一部分，它带着审计、带着版本、带着"谁能改谁能看"的分工边界。治理优先于调度的"先"，不只是时序上的先，是**层级的先**——造规矩的那一层，必须先于用规矩的那一层存在并负责。这也是为什么把治理和调度揉进同一层的系统，迟早会撞出那类"调度员顺手放宽了闸门"的事故：因为在那类系统里，没有一层是专门为规矩负责的。

## 六、对照 MCP 权限 / 编排框架：权限是闸门，规矩是宪章

主流框架怎么处理这个问题？MCP 把焦点放在"调用时的访问控制"上：这个工具谁有权调，那个资源谁有权读，权限表附在动作的那一刻。编排框架则把注意力放在"流程怎么编排"上，权限常常只是外围配置。

我要把两者在 Multi-Agent 里重新排位：权限是闸门，它只管"这一刻能不能碰"；规矩是宪章，它管"这一单到底该不该存在"。前者回答"谁有钥匙"，后者回答"这扇门为什么该开"——两者都不是附在调用那一刻的小检查，而是派活之前就该被卷宗复核的硬账。

一旦把规矩降格成"访问控制的附庸"，就会出现最典型的事故：Agent 能调用某个权限，就顺手用了，没人回头问"这单本来就该不该发起"。Multi-Agent 要的，是让宪章级别的问题，在调度之前就被拦下来，而不是等权限表在关键时刻放人进去。

举个例子，权限表和宪章的差别就在一念之间 `[内部项目实测]`：一个只读 Agent 的权限表里被人顺手加了"读生产配置"的授权，理由是"查一下参数也方便"。权限层面它确实"有这个能力"，一次抽查时它读到了不该外流的接口回包，写在判定里还被自动归档——权限表放行了"能不能碰"，却没人在调度前问过"这单该不该碰"。事后我们把"生产配置单读"从权限表里摘掉，加进宪章层，标成`需双签 + 留痕`，同样是读数据，性质就从"顺手的便利"变成了"受规约管辖的动作"。这就是权限（闸门）和宪章（规矩）从纸面区分到机器落地的差别：前者只回答能不能，后者界定该不该，而 Multi-Agent 真正要管的是后者。

## 七、原理飞升：先立规矩，再派人

收进主线，第八篇在 Multi-Agent 里的位置是这样一句话：

> **治理优先于调度。** 调度决定任务怎么流，治理决定什么该流；Multi-Agent 敢不敢自称可证明，取决于它的规矩是不是在派活之前就被机器验证过，而不是靠调度员临场把闸门开大。

诚实地讲，把规矩做成前置闸门，短期又像在拖慢速度：多一道派活前的核验，多一层 MCP 权限的复审，看着都是流程税。可这正是 Multi-Agent 和"Agent 玩具"的分界。玩具能接受"调度顺、结果差不离"，Multi-Agent 一旦放过规矩前置，就是在给不可证明的链盖合格章——后面所有复核，都是在替一个超纲请求收拾残局。规矩前置，是让 Multi-Agent 对范围负责的第一道关。

这也给第九篇递了棒。《人不进圈才是浪费》要回答：规矩与调度都立起来了，人到底该站在圈外当观众，还是该进圈当那个在关键处拉闸的人——HITL 不是妥协，是把 Multi-Agent 闭合成闭环的那只真手。

**谱系定位**：这一篇直接把"Agentic RPA / 企业 Copilot"那一格拉了进来当参照——那些系统把治理落在"调用时刻的访问控制"上，权限到位就放行。Multi-Agent 要求的治理更高一档：规矩要前置成门禁，宪章问题先于调度被拦，这跟 MCP 工具生态里"谁能调哪个工具"的授权模型是两回事。我们也没有天真到在"多 Agent 辩论·对抗"那种高信任环境里省略治理——恰恰相反，越容易互相甩锅的对抗链，越需要先立规矩再派人。治理不是调度员的良心，是被机器的规则系统先验证过的边界。
