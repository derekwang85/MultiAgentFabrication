# Multi-Agent vs Subagent：都是人从众？

> 既然 Codex、TRAE、OpenClaw 都能派"子智能体"同时开工，"多智能体"也就实现了，为什么还有这么多人折腾这两个概念？子智能体Subagent和多智能体 Multi-Agent 的区别：一个是主控临时伸出去干活的手，一个是元层 / 产品层里具有独立判断和思维能力的责任组织。前者是被调用的执行分身，后者是让判断可分工、可校验、可审计的组织。

---

## 一、两种"影分身"

看起来一样的忍术，有些一碰就碎，有些能够以多打少，同样看起来一堆Agent，可能也是天壤之别。

如果要一对一地跟一个 Agent 聊天，让它把一段代码修好、把一篇文档写完，你多半不会碰到"subagent"这个词。可一旦你打开的是 Codex、TRAE、开源的 OpenClaw，就很大可能看到主控旁边挂着几个并行的子 Agent（或者在运行时由主控召唤），它们各占一块画布、各自跑一轮、把结果交回主窗口。看起来和你要做的"多 Agent"没有区别：都是"一群 Agent 分工干活"。

于是常会听到这句话：**"这不就是 subagent 吗？"** 语气里带着"多 Agent，确定不是在重复造轮子？"的意味。

这句话是一个真实的反馈：两种东西在"一群 Agent 一起出现"这个最粗的粒度上，长得一模一样。如果只看"有没有分身"，你确实分不开它们。我希望把镜头推进到能看清区别的地方：**Codex / TRAE / OpenClaw 的 subagent，和 Multi-Agent，是两种不同性质的东西。** 看得越细，越会发现不是"重复造轮子"，而是"像一辆车和整条装配线的差异，它们根本不是一个物种"。

## 二、执行分身，不等于责任组织

**Subagent（执行分身）** = 主控为了完成某个任务，临时调出来干活的最小执行单元。它没有自己的账本，没有长期记忆，没有"我要对什么负责"的自我定位——它是主控的一只手，主控想让它干什么它就干什么，干完即弃，生命周期就是那一次调用。

**Multi-Agent（责任组织）** = 元层 / 产品层里一组有分工、有问责、有记忆归属的判断主体。每个 Agent 不只"干活"，还背着一份"这项判断凭什么可信、坏了能追到谁、经验沉淀到哪一层"的账。它的生命周期贯穿多个会话，记忆分层归属，决策留痕。

一句话对照：**subagent 解决"主控的一只手怎么伸出去"，Multi-Agent 解决"一群判断怎么组成一个可证明的组织"。** 前者是把一个指令拆成几次执行的"语法糖"，后者是把一个不透明的判断黑盒改造成可分工、可校验、可审计工艺的"系统工程"。二者最深的差别就在这里：subagent 是**执行的并行化**，Multi-Agent 是**判断的责任化**。

理解定义，不是口舌之争，它决定了你会不会踩进一个深坑。下面的八维拆解把这件事展开。

## 三、八个维度把"看起来一样"拆开

用八根维度，把两种"分身"逐根对照。前四根来自最日常的直觉，后四根逼着你去看系统的骨架。

| 维度 | Subagent（执行分身） | Multi-Agent（责任组织） |
|------|--------------------|--------------------|
| ① 架构位置 | 主控下面的原语，一次调用 | 元层 / 产品层的责任主体，持续存在 |
| ② 生命周期 | 瞬时：这次任务结束即回收 | 持续：跨会话、可演进、可被问责 |
| ③ 决策权责 | 单点听令：主控拍板，它执行 | 分散可责：判断可分工、可校验、可审计 |
| ④ 大模型调用 | 复用主控的同一套能力，即取即用 | 求解：把"选谁干活"建成约束求解 |
| ⑤ 可塑性 | 一次性：跑完就没了 | 可演进：能从错误里长出更稳的规矩 |
| ⑥ 记忆归属 | 用即弃：无长期记忆 | k1-k4 分层：谁的记忆算谁的，带溯源 |
| ⑦ 可证明性 | 直接采信主控，无从独立验证 | 隔离三权验证 + 门禁，宣称对齐事实 |
| ⑧ 可追溯性 | 不留痕：跑过即验收 | decision.db 留痕 + ADR + 人工终裁 |

把这八根并排放，你会看到一条清晰的裂缝：**左半边（①–③）只关乎"一套工具好不好使"；右半边（④–⑧）已经在回答"这套系统值不值得信、会不会悄悄变坏"。** 前四个高度是"工程效率"的维度，后四个早滑进了"治理与记忆"的维度。

### 被人记错的四个维度：为什么直觉会骗你

关于"大模型调用"，最容易记反。**Subagent 的实现恰恰用的是"复用"**——它不是为每个子任务去求解哪个模型更合适，而是复用主控面前那个模型、把上下文切开并行处理。Multi-Agent 反其道而行之：它把"这个任务为什么交给这个模型"从拍脑袋改成*多维约束求解*（严格过滤 → 渐进松弛 → 显式失败），让每一次选型都留下可复核的约束依据 `[内部项目实测]`。你以为是"Multi-Agent 在复用、subagent 在求解"，其实正好颠倒。

关于"可塑性"：subagent 跑完一轮，经验即蒸发，系统不会因此变得更强，它只是把同一个主控的力气多使了几遍。Multi-Agent 的系统里，产品层跑出来的经验会沿记忆带审计、有人终裁的单向管道回灌成元层下次造系统的规矩——**它是一台会把自己越造越好的机器，而不是一台反复找你帮忙的机器。**

关于"可证明性"：subagent 的产出，主控直接采信；Multi-Agent 的产出，要到和被修复方**隔离的三权验证者**那里，做不预设立场的验收——验证者不知道修复时的思路，只看交付物合不合规格 `[内部项目实测]`。前者把"相信"放在主控的一次执行里，后者把"相信"拆成一道能跨层复核的门禁。

关于"记忆归属"，这是 Multi-Agent 真正舍得下本钱的地方。subagent 没有记忆，或者说它的记忆就是主控发给它的那几段上下文；Multi-Agent 把记忆按 k1 规则 / k2 会话 / k3 长期情节 / k4 跨层回流切得清清楚楚，并且写死两条边界：**元层只读 k1、k2，不信 k3；产品层才读 k1、k2、k3。** subagent 连"该不该有记忆"这个问题都没有，Multi-Agent 已经把"谁的记忆算谁的"当成一等公民在设计。

### 前四维也不是纯效率：一个静悄悄的越界风险

别急着说"前四个维度只是工程差别"。正是①架构位置这一维，藏着最高危的一条：**subagent 经常被赋予"工具可读写、上下文可共享"的自由，而它又没有独立的账本。** 一个能读写全局记忆、又能调用工具、却没有独立账本的执行单元，在长期运行里实际上已经具备了"改自己想看到的规矩"的能力——只是没人把它点破。Multi-Agent 用分层和隔离，把这个静默的风险物理上关起来。subagent 不是"低配的 Multi-Agent"，它是 Multi-Agent 要专门防范的那种失控胚子。

## 四、选择 Multi-Agent

既然 subagent 也能"并行、分工、产出"，为什么 Multi-Agent 非要重起炉灶？

因为随着任务复杂度和项目的扩大，想要用较少的 HITL 快速地完成尽量多的工作，Multi-Agent 具备三个层次的对比优势：

**第一层，工具 vs 组织的对照史。** 认知科学家梅林·唐纳德（Merlin Donald）在讲人类认知进化时，区分了"个体用工具的能力"和"个体把认知外化、共享、沉淀成集体公共记录的能力"——后者让他看见一种不同于个体心智的"社会性的思维"。这个区分迁移到 Multi-Agent 上恰好成立：**subagent 是人类个体"伸手用工具"的平行版；Multi-Agent 是唐纳德说的那种"把判断外化成可共享、可追责的公共资产"的组织化版本。** 你不可能用一堆临时抓来的手，拼出一个有记忆、可演进、能被审计的体系——因为它们当中没有一个是"负责的"，它们只是"被调用的"。

**第二层，效率轴 vs 信任轴。** 主流框架和 Codex / TRAE / OpenClaw 的 subagent，共同处在"怎么把分工编排出来"的效率轴上；Multi-Agent 站在"怎么让分工可信"的信任轴上。两轴不冲突，但**subagent 能大幅优化前者、却天然缺席后者**。如果你要的只是"把一次大任务拆成几只手并行忙完"，subagent 是对的；如果你要的是"这套系统交付之后，你信它、能证明它、它不会悄悄变坏"，subagent 给不了——它根本没有那本账。

**第三层，谁的记忆算谁的。** subagent 的记忆跟着主控的上下文走，用完即弃，谈不上归属；Multi-Agent 的记忆是分层的资产。**subagent 是一次次重新算，Multi-Agent 是持续地记账并拿账本反哺下一次。**

**subagent 是主控伸出去干活的手，Multi-Agent 是让判断可分工、可校验、可审计的责任组织。** 选择效率的时候选择 subagent 也能接受，但是选择信任的时候只能选择 Multi-Agent，尤其是在构建一个复杂系统的时候。真实的生产系统里，Multi-Agent 完全可以内嵌 subagent 式的执行分身去干脏活累活；但反过来，**你永远无法用 subagent 拼出 Multi-Agent**，因为它们缺的不是数量，是"责任"这件东西。

## 五、执行的并行化 ≠ 判断的责任化



> **Subagent 解决"执行的并行化"，Multi-Agent 解决"判断的责任化"。** 前者是主控的临时分身，后者是判断的责任组织；真正的分野不在"有没有分身"，而在"有没有账本、有没有记忆归属、有没有可证明与可追溯"。凡是没有这四样却自称多 Agent 的，都还停在"工具层"。

## 第一天就能用的清单

- [ ] 下次看到"能派子 Agent"的工具，别急着说"这就是多 Agent"——先问三件事：它在哪一层（执行分身还是责任组织）？有没有账本（记忆归属）？产出的"信"从哪来（可验证还是直接采信）？
- [ ] 如果只是把一次大任务并行跑完，直接用 subagent 式的执行分身；只有当你要"交付后仍可信、可演进、可审计"时，才值得动手搭 Multi-Agent 的分层记忆与隔离验证。
- [ ] 给你的系统判断一句：这些并行的"分身"里，有没有任何一个"对结果负责"？如果没有，它再并行也只是执行加速，不是多 Agent——缺的不是数量，是责任。
