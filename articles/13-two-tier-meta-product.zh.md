# 两层 Agent：造系统的，与在系统里的

> 大多数人多 Agent 架构只问"一群 Agent 怎么分工"，却很少问另一句更前置的话：这群 Agent 是谁造出来的？在系统里的 Agent 再能干，也造不出那个能放进生产、能验收、能改规则的自己。Multi-Agent 要立的第二根梁，是把"造的层"和"用它的层"分开，并让两层各有各的记忆，记忆在两层之间只走一条带审计的路。

## 一、最常被问错的一句：Agent 该怎么分工

"多 Agent 该怎么分工？"——这个问题我问过自己很多年，直到在一个多 Agent 专业研投、跨团队知识同步的项目里，才意识到它问错了地方。分工是第二层的问题，第一层的问题是：**这套 Agent 是从哪儿来的？**

答案藏在两套被摆在一起、却常常被当成一层的概念里。一套叫"造 Agent 的 Agent"，一套叫"在被造的软件里干活的 Agent"。前者像建筑工人又像工厂，它把软件组件一个格子一个格子地搭出来；后者是前者制作出来的"专家角色"，被放进了目标产品，在真实的请求流里当班。我管前者叫**元 Agent**，管后者叫**产品 Agent**。

这两层有一个决定性的不对称，大多数人把它抹平了：**元 Agent 先于产品 Agent 存在。** 产品 Agent 只会处理"现在该对这份输入做什么"；元 Agent 要背着"这个东西将来凭什么能信、坏了怎么修、规则怎么改"这一整本账来开工。把两层混成一层来设计，几乎必然出两种病：要么产品 Agent 被赋予"能造自己"的能力，制造出不可审计的黑洞；要么元 Agent 被当成普通干活 Agent，造出来的东西没人验证、没法升级。Multi-Agent 能否自称可证明，取决于它清不清楚自己此刻是站在哪一层。

## 二、元层是工厂，产品层是车间：流水线的两道闸

在一个实际的多人多 Agent 协作系统里，我把这两层各画成一条流水线，中间夹着一道"产物下发"的手递手 `[内部项目实测]`。

元层这一侧，是开发态的建造流水线：先由规划角色把活拆成带验收口径的 WBS 单，再把资源分配成可并行的子任务，交给一组**无状态的执行子 Agent** 去跑，最后由一个和被修复者**隔离的三权验证者**来验收——它不知道修复时的思路，只看交付物合不合规格。这一整段在出门之前，还要过一道能拦住"写得像、其实没签字"的门禁。只有过了这道门的产物，才允许被下发到产品层。元层产出的不是"一段给你参考的建议"，是"一份已经过检、可直接接入的零件"：规格、因子、测试用例，落地即成正式输入。

产品层这一侧，是运行态的当班流水线：请求先被一个**意图路由器**将来意判别到对应的专家角色上，再由一套**角色注册表**里注册过的多 Agent 专家去执行。执行不只有一条快路径：普通的"顺序链路"一路往下办理，关键的、不能只凭多数一致的判定，则走一条**隔离对抗**的并行通道，让对立观点各占一角、把分歧原样保留下来，而不是强行融合成一个"大家都同意"的中间值。跑完的每一步都落进一本**决策库**，灌出"该不该采纳"的建议——但建议永远只是建议，最终决定权在圈外的人工手里。

这条"元层造好、产品层接走"的骨架，就是 Multi-Agent 的车间结构。两层共用一张蓝图，但各有各的负责对象：元层对"能不能交付"负责，产品层对"产出的判定对不对"负责。

## 三、记忆分四层：谁的记忆算谁的

分完 Agent，接下来才是更硬的问题：**记忆归谁？** 很多系统把"记忆"做成一张大坑，什么都在里面倒，然后抱怨 Agent 越跑越乱。原因就是没分清记忆是挂在哪一层的。

我沿用一套四层知识总线的分层，把它当作记忆体系的骨架：

- **k1 规则层**：宪章、编码十诫、方法论、红线。静态，文本可审。它的规矩是"进场必须带"——每次开工、每个会话开始就注入，不是等用的时候再查。
- **k2 会话工作记忆**：当前这轮对话的滚动上下文，用一个滑动窗口摘要收拢，超限就压缩，扛不住就安全丢弃。它只管"这一场"。
- **k3 长期情节记忆**：这是会沉淀下来、跨会话复用的那部分。按"偏好 / 策略上下文 / 标的 / 裁决"四类长期记忆分开存放，每条带溯源、带置信度、带去重哈希——能证明"这条是从哪一次运行来的、可信几成、有没有重复"。
- **k4 跨层记忆回流**：这条不是存记忆，是**运记忆**。它连接元层与产品层，把产品层跑出来的经验，回灌成元层下次造东西用的规矩。

这套分层的价值，不在每层的字段设计，而在它回答了两个"谁的记忆算谁的"的边界：**元层只读 k1 和 k2，它不信 k3**——因为它造系统，不背运行期的旧案；**产品层读 k1、k2、k3**——因为它当班，需要那些长期沉淀的判断上下文。一个只造不用的层，不该被运行期的记忆拖着走；一个只在车间当班的层，才有资格读那份长期账。

## 四、k4：一条只有一条路的回流管道

四层里最容易被做坏的，是 k4。因为一旦产品层能直接往元层的规矩里写东西，"造的层"和"用它的层"就又糊成了一层，前面所有分层全部白做。

所以 k4 被设计成一条**单向、带审计、有人终裁**的管道，而不是一个可以来回倒的水池 `[内部项目实测]`：

- **单向**：经验只能从产品层流向元层。产品层跑完一次，把"这次为什么这样判、代价几何、下次能不能更稳"留成一条待提炼的经验；元层负责决定要不要把它升格成规则。方向反了不行——元层不靠产品层的旧账来现场拍板。
- **带审计**：任何一条经验升格为规则，都必须走 ADR 变更留痕，写入版本化的记录里。规则不是被某次好结果"感动"出来的，是被证据和评审钉进去的。可回滚。
- **有人终裁**：自动提炼可以做，把"要不要真的改规矩"这一刀的裁量权，始终留给圈外的人工。机器把候选经验和证据摆上桌，人判断值不值得改、改了会不会伤到别的零件。

这条"只进不出、带账本、人拍板"的回流管道，才是记忆体系里真正让 Multi-Agent 闭环的那根梁。没有它，多层记忆就算分得再细，也会在"经验→规矩"这一步上塌成单层。

## 五、治理红线：记忆不是垃圾桶

记忆本身也会生病。Multi-Agent 给记忆系统上了八道横切的红线，条条都是走过弯路的教训 `[内部项目实测]`：入库必须带内容哈希去重，防止同一教训反复沉淀占满上下文；每条长期记忆必须标置信度等级，让读它的人知道这条可信几成而不是一律当真；必须有来源 run 编号做溯源，出事能一路追回；注入时有条数上限做边界，防止上下文被旧账撑爆；删除必须人工，不许 Agent 自己洗掉不利于自己的记录；规则变更必须走 ADR，不能悄悄改闸门；记忆服务不可用时系统要能降级运行，而不是整条链卡死；参数快照要哈希留存，保证同一输入能重放、判定能复现。

这些红线看着琐碎，其实共同守住一句话：**记忆是资产，不是垃圾桶。** 资产要能溯源、能验真、能定价；垃圾桶只要装得下就行。Multi-Agent 敢不敢把自己的记忆当资产交给产品层去读，取决于它有没有这八道闸。

## 六、对照：为何不能把两层做成一个池子

主流的 Agent 编排框架，默认模型是"一个注册表里登记一堆角色，谁都能互相调用"。这不是错，但它把元层与产品层压扁成了一个平面：谁都能造、谁都能改、谁都能读所有人的记忆。在原型阶段这很爽，一旦进了生产，就会撞上那个反复出现的坑——**一个能读写全局记忆、又能调用工具的 Agent，实际上已经具备了"改自己想看到的规矩"的能力**，只不过没人把它点破。

Multi-Agent 的对抗思路是：承认这种能力天然存在，所以干脆用分层把它关起来。元层不读产品层的长期记忆，产品层不写元层的规则，两层之间的记忆只走 k4 那条带审计的单向管道。这比"靠提示词约束心怀不轨的 Agent"要诚实得多——你不需要相信一个 Agent 不会越界，你只需要让它物理上够不到那边。分层不是为了让架构变复杂，是为了让"谁能碰谁的记忆"变成一个可审计的问题，而不是一句"大家都交付，应该没关系"的赌注。

## 七、原理飞升：造系统的与在系统里的，记忆各自记账

收进主线，第十三篇在 Multi-Agent 里的落点是这一句话：

> **两层 Agent。** Multi-Agent 的可靠性不只见于它产品层的分工有多细，更见于它是否说清了元层与产品层各自的边界与记忆：谁在造、谁在当班、谁的记忆算谁的，以及经验只能沿着一条带审计的单向管道回流。能分清这两层的系统，才谈得上把"造系统的判断"也纳入可证明。

诚实地讲，分层会带来成本：元层与产品层之间多一次交接、k4 回流多一道 ADR 与人工终裁，看着都像流程税。可这正是 Multi-Agent 和"Agent 玩具"的分界。玩具用一层池子装下一切，Multi-Agent 偏偏要砌两堵墙——因为它知道，判断力最危险的时候，就是某个人能同时当好"造系统的人"和"在系统里干活的人"、还觉得自己用的是同一套账的时候。Multi-Agent 选了两套账，并且只开一扇带锁的窗来让经验流动，这就是它对"可证明"最诚实的交代。

这也给下一轮递了棒：双层与记忆手递手立住了，接下来要回答的是，这一整套"造厂的厂"本身，如何持续长大的问题——Multi-Agent 不再只是"人 + 一批 Agent"，而是一台会把自己越造越好的机器。

**谱系定位**：这一篇站在谱系里最接近生产的格子收尾——凡是"SWE Agent / 企业 Copilot"里真正要长期上线的多 Agent 系统，几乎都会撞上同一个坑：把元层（造系统的）和产品层（在系统里的）揉进同一个池子，谁都能造、谁都能改、谁都能读所有记忆。单层池子对原型很爽，对生产是隐患。我们刻意没有把这一篇套到"RAG / 研报自动化"那种较短的链上——链条短、角色少时，双层架构的交接成本大于收益；双层是为了在判断真正值钱、链又长得失控的场景里，把"谁能碰谁的记忆"变成一个可审计的问题。
