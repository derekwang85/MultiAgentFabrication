# 选型是求解

> 排错时最顺手的兜底，正在悄悄拆掉你整条链的可证性——选模型不是搭 fallback 栈，是一次约束求解。

## 一、那个万能的 fallback，是我自己设的雷

我做多 Agent 的第一套系统，选型是在最快的时间里拍出来的。哪个模型跑得快就用哪个，跨域的问题答不准，就写一句"这个走另一个 Agent"。当时的逻辑听着很合理：短板补上，长板继续用。后来系统越叠越大，我回头数了一遍"兜底规则"，数到一半不数了——因为每一层兜底，都是一次没有人能指认的判断。

问题出在"谁兜底的"这件事上。fallback 写进配置那一刻，等于告诉系统：模型 A 答不好，就静默换 B 去答。可 B 为什么更合适？依据哪条约束？没人问过。真正让我警觉的是某一次排障：一个看似该由小模型完成的任务，被系统悄悄升级给了大模型，token 多烧了三倍，线上那张"我用了小模型所以便宜"的结论当场作废。那时候我才明白，fallback 不是工程手段，是被我一直逃避的选型问题——我把它藏进了运行时的兜底逻辑里，等于把该在选型时做的决定，推迟到出错时才含糊地补。

这给第四篇立了个靶子：**选哪个模型、组什么样，不该靠直觉拼拼图，更不该用 fallback 兜底来掩盖没想清楚的选型。** 它应该被当成一次约束求解：把需求写成约束，让小成本算法自己筛出唯一解，筛不出来就宣告失败，而不是顺手掏一个"能跑的"。

## 二、把选型当成约束求解，而不是堆清单

我切换到"约束求解"这个框架，是因为它逼我把"要"和"必须"分开，而这正是 Multi-Agent 在选型这个节点上需要的纪律。一条链上下一环的可靠性，取决于上一环拿出的结果是不是基于硬性约束筛出来的，而不是"看起来差不多"。

做法分三步走（图 1），对应一组逐步收紧的约束：

- **严格过滤，只留硬约束的幸存者**。先写不可妥协的硬性约束——成本上限、合规要求、上下文窗口门限、本地可部署。不满足就直接淘汰，不留"勉强能用"的幸存者。这一刀最狠，也最省心，因为硬约束不收买人情。
- **渐进松弛，软约束打分排序**。硬约束筛完之后往往还剩好几个，这时候启用软约束（延迟、质量分、厂商生态），给它们打分排序。规则写得越明确，排序越能复核；规则说不清的地方，就是下一轮要显式失败的位置。
- **显式失败，无解就宣告无解**。当约束彼此冲突，筛到没有候选，标准做法是宣告"No solution"，把冲突摊开给人看，而不是塞一个模糊兜底。显式失败是约束求解和非约束方案的真正分水岭：它把"没法选"也当成一个可结论来交付。

为了让它可真验证，我给自己立了个"漏斗最小输入/输出的契约束"：每一层收进什么、吐出什么，都必须能被记录、被回放。

- **输入必须可声明**。硬约束得写得出可判定的字段——`成本上限≤N`、`上下文窗口≥M`、`合规白名单∈{…}`。写不出字段的"约束"，其实还不是约束，只是一句愿望。软约束同样要量化：延迟给阈值而不是"要快"。
- **每一层都要吐一行证据**。严格过滤吐"本次淘汰 3 个候选，均因成本上限超 N"；渐进松弛吐"打分排序，软约束偏好的此刻理由"；显式失败吐"候选集为空，冲突双方是约束 X 与约束 Y"。这三行拼起来，就是选型节点的留痕记录。
- **输出只有一个幸存者或一个无解**。漏斗要么交出一个带证据的选型结论，要么交出一个摊开冲突的"No solution"。中间态的"差不多能跑"都不许出现，因为它既没有证据，也没有结论。

这套三步在智能体编排里尤其好用，因为在多 Agent 里"选型"不是选一次，而是每个节点、每次任务都可能发生。路由到哪个角色、调哪个模型、给多大温度，全都是一次小选型。把它们统一成"约束求解"这一种范式，意味着全链的选型决策都能被同一套审查逻辑对上，你才敢把任何一个节点交给自动调度。

## 三、对照 LangGraph：求解思维到底多收窄了什么

为了讲清楚这不是纸上谈兵，我跟 LangGraph 的选型思路比了一次。LangGraph 把编排讲成"图 + 状态机"，条件边、路由器、tool 调用，写得很完整，它的优势是结构清晰、可调试。但它的判断逻辑，默认是开发者手写的 if/else，或者丢给一个 LLM 路由器临场决定走向。

跟"约束求解"对照，差异落在三处：

| 维度 | LangGraph 手写/LLM 路由 | 约束求解三元组 |
|------|------------------------|----------------|
| 依据 | if/else 或模型临场倾向 | 显式的硬/软约束 |
| 失败时 | 往往落到兜底分支 | 显式失败，摊开冲突 |
| 可复核 | 依赖开发者写了什么 | 约束即证据，可回查 |

LangGraph 教了我"把流程画成图"，但它默认的选择逻辑，恰恰是最容易退回 fallback 的地方。我并不是说它错，而是说：给 Agent 一条"图"还不够，得再给它一套"约束求解"的裁决器，图上的每个分支为何这么走，才有一份可审计的依据。主流框架把这层留给了开发者自己补，而这层正是 Multi-Agent 选型环节缺的那块砖。

退回去看，两条默认路径各有各的代价。手写 if/else 是"可审计但呆板"：每一条分支你都写得出，出事能回查，但它表达不了权衡——成本阈值降到多少、延迟让出多少，都是写死的，改一次要动代码。丢给 LLM 路由器是"灵活但黑箱"：它能在临场权衡，但你看不到它依据哪条约束下的决定，出错了你也只能反问模型"你当时为什么这么走"，而它给你一个事后圆出来的理由。这两条路，一个死于刚性，一个死于不可复核——恰好落在一个需要"既要灵活、又要留痕"的节点上。约束求解在中间补的那刀，正是"由约束 + 打分 + 显式失败"来决定分支，而不是由代码的硬编码或模型的临场感觉来决定。

## 四、无为而治：把约束写清楚，选型自己会解

选型这件事我后来悟出一个不太像工程的说法：**好选型在于你把约束写清楚，剩下的交给系统去解，你越少在运行时"亲自下场"，链越干净。** 这跟老子的"无为而无不为"是一个意思——看似什么都不做，其实是把该定的规则都定好了，让机制自己运转。老话讲"治大国如烹小鲜"，火候是靠规矩调出来的，不是靠厨师在旁边不停翻搅。多 Agent 的"无为"，就是选型阶段一次把约束收紧，运行时就不再需要手忙脚乱地兜底。

反过来说，那些运行时到处救火的系统，本质是选型阶段"有为"过度、约束阶段"无为"不足——全凭临场判断，等于把规则压力全部转嫁到每一次出错的瞬间。Multi-Agent 要的是一套能自己求解的约束，不是一套靠人肉兜底的补丁。

说回可证性。约束求解的每一层筛选，都留得下"依据哪条约束作出取舍"的证据——硬约束筛掉的是谁、软约束为何此刻偏心某个候选、最后一步显式失败暴露了哪对约束冲突。这些证据串起来，就是选型节点的审计链。它跟第三篇的三轨三权接上了：分工切开的环节，还需要选型时的约束证据，才能让"可审计"落到每一个取舍上。

## 五、显式失败，是把"选不出来"也当成一份交付

这一步是最反直觉、也最容易被糊弄过去的。很多人嘴上说"我做了显式失败"，但做出来的是个伪解决：他们让模型"尽力给一个答案，实在不行再说 No solution"。结果模型永远是"尽力"，因为"尽力"是一条没有任何硬性的底，它永远能编出一个看着像答案的东西。真正的显式失败，是让"无解"和"有解"一样，成为漏斗里一个合法、可交付、需要有归属的输出——它不是系统瘫了，是你把约束问到了彼此冲突的边界上，这一步本身就是结论。

这里有两条一般人容易掉进去的坑。第一是"显式失败后谁来裁决"。约束冲突摊开给人看，但收到冲突的人不认识系统、也未必懂约束，等于把石头交给不会看的人。所以我定的规则是：No solution 不是终点，它必须带着冲突双方属于哪两条约束、各自有多硬、放弃哪一条的代价是什么，一起交出去——裁决的人只做取舍，不做考古。第二是"伪显式失败"。有的系统把"No solution"也当字符串拼进 prompt，让模型自己决定说不说，这等于把裁判权又还给了黑箱。显式失败必须是硬代码判出来的：候选集数学上为空，就必然走无解分支，中间没有任何模型插话的空间。

跟"无为"对照着看会更清楚。约束求解要你"有为"的地方，恰恰是把边界写死、把无解这条路也定死；你越早承认有些选择就是无解，而不是运行时硬着头皮兜一个，链上每个节点的可信度才站得住。这也是 Multi-Agent 选型环节最诚实的一张底牌——宁可今天说 No solution，也不肯上线后留下一串查不到来路的兜底。

## 六、原理飞升：可解的选型 = 硬约束 × 软约束 × 显式失败

把第四篇收进主线，选型在 Multi-Agent 里的位置就清楚了：

> **可沉降的选型 = 硬约束筛出可能解 × 软约束排出最优 ≈ 显式失败兜住无解。** Multi-Agent 的每个节点都要做选择，而选择要想可审计，就必须走这一条约束求解的漏斗——不筛就用,是透支；无解还硬兜，是造假。

诚实地讲，约束求解有它的代价。它要求你把需求翻译成约束，这一步本身要花时间，有时候还不如拍脑袋快。但代价买来的是 Multi-Agent 最要紧的那件东西——**每一次取舍都有来路**。小系统靠直觉选型没问题，因为出了错还能人肉复盘；一旦链变长、节点变多，没有约束证据的选型，就会成为线上那些查不到来路的 bug 的温床。

这也给第五篇递了棒。《约束即配置》要把"选型是求解"落到配置层：既然选型是一堆约束，那约束就应当可声明、可审计、可演化——把"加模型"变成"加配置"，而不是往代码里堆 if/else。多 Agent 从"选得对"，往前走一步到"配得清"。

**谱系定位**：在 Agent 应用谱系里，这一篇站在"SWE Agent / 编排框架"这一格——凡是要让多个模型、多处路由共事的系统（CrewAI、AutoGen、LangGraph 这些编排器，以及把多 Agent 塞进一条长链的编码助手），都绕不开"这条路为什么交给这个模型"。我们没有覆盖"Agentic RPA / 企业 Copilot"那格——那种场景人的审批位通常已经是硬约束，选型问题会被更大的流程问题盖住，它的解在第八、九篇。把选型当成求解、而不是堆清单，正是 Multi-Agent 和"编排框架默认的 fallback 思维"分野的第一刀。

- [ ] 把系统里每一处 fallback 找出来，问一句"这条兜底依据的是哪条约束"——答不上来的，就地改成显式失败。
