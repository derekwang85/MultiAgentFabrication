# 约束即配置

> 加一个模型，不该是去改代码——只有当模型画像是一份数据、约束是一行配置时，链上的每一个选择才都留得下来。

## 一、加一个模型，竟然要动代码

那是我多 Agent 系统里最奇怪的一次改动：需求只是"再挂一个本地小模型进去"，我却顺着一股惯性摸进了一堆 if/else。哪个任务走大模型、哪个走小模型、哪个要 temperature 低一点，全都散落在路由分支里。加模型这件本该"填一张表"的事，最后变成了一次手术。

更糟的是第二天我去复核，发现自己已经说不清：这几行 else 是谁在什么场景加的？它依据哪条约束？我当时只是"觉得"该这么走。配置和代码搅在一起，判断的来路就没法看了。

我给第五篇立个靶子：**选型是一堆约束，而约束不该烂在 if/else 里，该住进声明式配置里。** 加模型 = 加配置，而不是改代码。

## 二、约束是数据，不是逻辑

第四篇说选型是约束求解。那约束住哪里？答案是把它们声明成数据——一份能被读、被查、被改的画像（schema），而不是埋在路由函数里的分支。Multi-Agent 要的是"可审计的取舍"，而可审计的前提，是每一次取舍都能指向一行看得见的字段：这次为什么走这个模型？因为它的硬约束达标记录就在这里。

声明式画像至少管住三件事：

- **字段即依据**。硬约束、软约束权重、显式失败标记，各占一栏；裁决时刻照着字段走，不靠临时手感。
- **数据即证据**。一次裁决留一行，对应哪条约束可回查；这就是第三篇三轨制里"审计链"在配置层的落点。
- **配置即演化**。想换模型、调成本，改一行数据，代码一行不碰——链路稳定性因此上了一个台阶。

这套"把判断写成声明、靠机制去解"的做法，正是多 Agent 和单个 Agent 在工程上最不一样的地方。单个 Agent 调 prompt 就是全部；多 Agent 节点一多起来，每个节点的选型约束都写死在代码里，链就变成一团改不动、也查不清的毛线团。

有一个具体的演化场景最能说明"配置即演化"为什么值钱。假设线上有一个任务长期走 token 费用高的那个模型，某天上游模型镜像出了问题，你想临时把这类任务切到便宜模型顶上。代码里写死的路由，你要么去翻散在各处的分支、逐个改逐个测，要么写一条新的兜底规则——而这条兜底规则，恰恰又是第四篇说的那种"没人能指认的判断"，埋下去的就是下一颗雷。声明式画像里你只需要改一行软约束权重，让"此刻成本更敏感"显式生效，调度层照着字段自动收敛，改了什么、什么时候改的、依据哪次需求，全部留在配置变更记录里。一次应急，从"人肉翻代码"变成"改一行数据 + 一行留痕"，这就是判断阶梯上"可审计的取舍"落到配置层能买的到底是什么。

## 三、SmartQuant 的声明式画像

在 SmartQuant 和 derekcoding 里，我把选型约束做成了"声明式画像"。每个模型是一份画像：硬约束标明它必须满足的门限，软约束给出排序权重，最后留了显式失败的出口。调度层不写"如果任务像 X 就跑 A"，而是把一个任务的参数交回画像，让求解器照着字段去解。

一份画像就五六行，[内部项目实测] 例如：

```yaml
model: quant-s
hard: { cost_ceiling: LE, context_window: GE, on_prem: true, compliance: in-allowlist }
soft:  { latency: 0.6, answer_quality: 0.3, vendor_ecosystem: 0.1 }
fail:  explicit        # 无解时走显式失败，不许兜底
```

读出来的意思很清楚：量化小模型必须成本达标、能本地跑、在合规白名单里，才进候选；之后按延迟、质量、生态打分；要是约束冲突筛空，就走显式失败。整张画像没有一行 if/else，全是能被审查的数据字段。硬约束字段和软约束权重，就是我在内部项目里 "字段即依据/数据即证据/配置即演化" 三栏表的落点——裁决照着字段走，留痕照着数据查，演化照着一行配置改。

效果是：加一个新模型，不过是在画像库里多落一行配置；调度逻辑一行没动，审计链反而变长了——因为每一次"为什么选它"都能指回画像里那一行字段。这套取舍我从内部项目复盘里验证过，结论很直白：**约束写成数据，判断才有来路；约束写成 if/else，判断就成了运气的替身。** [内部项目实测]

## 四、对照 LangChain / Ollama：声明式不是新发明，是欠账的补课

我必须诚实地讲，声明式配置不是我的发明，它是一门早就该补的课。LangChain 把模型抽象成了可配置的对象，Ollama 让换模型变成一条配置变更，主流生态早就默认"模型该被配置，不该被写死"。

可它们只补了一半。LangChain 给你一个能配置的 LLM 对象，但任务往哪路由、用哪个 prompt，往往还是退回手写 if/else，或者丢给模型临场决定。Ollama 解决了"模型安装"的配置，没解决"为什么此刻用这个模型"的配置。

这里的分野值得说破：**"对象可配置"和"决策可配置"不是一回事。** 前者是给每个工具开一个设置面板，你依然是人肉路由；后者是把"哪个约束、此刻、为什么让这个上"也声明成数据，机器才能照着复核。把模型抽象成可配置的构造器，只是把 if/else 换了个更整洁的写法，判断来路还是那根靠人记得住的弦。Multi-Agent 卡口的关键，从来不是"能不能改"，而是"改了之后，谁能指认这一次取舍的依据"——这只有把决策本身也搬进数据，才接得住。

真正把"声明式"推到极处的先例，是 Kubernetes。它做了件很反直觉的事：把运维从"跑这个命令"（imperative）改成"声明我想要的终态，让它自己去收敛"（declarative）。`kubectl run` 告诉你此刻执行什么，`kubectl apply` 告诉你想要什么状态。正因为状态是可声明的，它才可审计、可回滚、可演化——Kubernetes 把"配置即终态"做成了整个云原生的地基。

多 Agent 要学的正是这一课。我们不需要发明声明式，只需要不把欠的账继续欠下去：把"哪个模型能做什么、凭什么让位、无解时怎么办"这些约束，从路由代码里搬进画像里，声明成一块能被人审查的数据。Multi-Agent 要的不是一堆聪明的分支，是一份能被指认的配置。

## 五、强耦合里，配置演进才是真的贵

声明式配置不是免死金牌，它在一种情况下会失效：链是强耦合的。所谓强耦合，就是 A 节点做选择时，暗地里假设了 B 节点会怎么选、C 节点会怎么兜。这时候你改一行模型画像，等于在别处撕开一道没人声明的口子——因为别的节点还在按旧假设在算。配置从 if/else 里解放出来了，可假设还捆在代码里。要注意，强耦合和第四篇的"约束冲突"是两码事：约束冲突是明牌对着打，能被显式失败当场摊开；强耦合是暗牌错着用，改了 A 不知道 B 会跟着碎。前者靠显式失败接住，后者只能靠"所有选择都读同一份数据"来根治。

我踩过的那个反例就是这样。[内部项目实测] 我当时给链路升级一个新模型，规规矩矩在画像库里加了一行配置，调度逻辑确实没动；可下游节点里的一个路由函数，还写着"遇到 X 任务就给量化模型"，根本没读画像、也不认新模型。结果新模型上线后根本没被走到，排查时才发现是那个漏网的路由函数在截胡。修法不是再补一个 if/else 拦它的 if/else，而是把这条路由也改成读画像——真正的强耦合修正，是让所有选择都收敛到同一份数据上，而不是靠人肉去对齐代码里的假设。

这跟 Kubernetes 的"终态收敛"其实是同一件事。Kubernetes 的可审计，不在于它有一张声明文件，而在于它有个 reconcile 循环：声明了你想要的终态后，控制面会不停把实际状态往终态拉，每拉一次就记录一次。多 Agent 的配置要可审计，也得有这个"收敛回路"——声明是一张画像还不够，得有一个机制不断把实际选型拉回画像约束，并把每一次回拉记成一行留痕。没有这个回路，"配置即演化"就只是把命令式搬了个家，审计链照样断在那些没人查的角落。Multi-Agent 要的是一份"能被机制执行"的数据，不是一份"写了就完事"的数据。

## 六、原理飞升：可审计的配置 = 约束即数据 × 数据即证据 × 演化不碰代码

收进主线，第五篇在 Multi-Agent 里的位置是这样一句话：

> **可审计的配置 = 约束即数据 × 数据即证据 × 演化不碰代码。** Multi-Agent 的选型要可证明，约束就必须住进能被人读、能被人查、能随需求改的配置里——写死的 if/else 是透支，声明式的画像才是资产。

诚实地讲，声明式的门槛更高：你得先想清楚有哪些约束字段、各自的等级，这比随手写个分支费脑。但代价换来了 Multi-Agent 最要紧的东西——**配置改起来不碰代码，判断查起来不靠翻代码。** 小系统随手写路由没问题，链一长，命令式的毛线团就成了查不清来路的 bug 的温床。

这里也有一条诚实的边界：单一 Agent、链路很短、出错能人肉复盘时，声明式是多余的负担，写死反而更省。Multi-Agent 真正撑得起"约束即配置"，是从"错了也能当场复盘"这条免费退路消失的那一刻开始的——节点多了，人记不住每一次取舍，数据才补得上记性。而这个转折点，恰恰是 Multi-Agent 从"一两个 Agent"跨到"一群 Agent"的临界，也正是整条系列一直在追的那道坎。

这也给第六篇递了棒。《少数派也能对》要处理配置之外的第二个难题：就算选型约束都对、配置也声明清了，多数 Agent 达成的一致，是否就等于正确。多 Agent 从"配得清"，再往前走一步到"判得准"。

**谱系定位**：这一篇借力"MCP / 工具生态"这一格——正是工具生态把能力和参数推进了可寻址、可枚举的地带，声明式画像才有词可写；反过来，Multi-Agent 要求"配置即证据"，比工具生态默认的"能力即端点"多走了一步审计语义。我们也没有把它写成"RAG / 研报自动化"那一格的模板：那种单程检索+拼装的活，一份静态配置就够，声明式的收益会被其复杂度吃掉。真正要"约束即配置"的，是那条模型一变就要演进的链条——不碰代码改配置，判断才查得清来路。
