# 三条轨与三权

> 分工切开了判断，三轨与三权把它重新缝成能问责的账本——一条链，三条账，三双不同的手。

## 一、分工之后，第一只手掌是谁

第二篇我们把判断切开了。切片那一刻特别痛快：调度只派活、执行只论证、知识只留痕，每层都有契约，看起来工整极了。但切开只是上半场。真正让很多多 Agent 项目在"看似搭好"之后再次崩掉的，是切好了却**没人管得住**。

我说一个非常真实的场景。你切好了三层，然后让同一个 Agent 从头跑到尾：它拆了需求、做了论证、给了留痕,还顺手给自己打了分。你回头一看，全对上了。三份产物都在,却三份都是同一双手造的。这时候如果有人问一句"这次结论到底凭什么信"，它照样答不上来——因为**切开的环节虽然分开名字，复核的手却还握在同一个黑盒里。**

这就是第三篇要补的那块：分工解决"切得开"，三轨三权解决"切了还连得住、管得住"。前者让判断可切，后者让切开的每一环真正有人负责。用一句话立住全篇：**一条链，三条账，三双不同的手。**

## 二、三条轨：把三条账分开追

先讲"三条账"。我们都做过这样的项目：任务清单、bug 列表、测试记录划在一个表格里，谁想起来了就添一行。混乱的根源不是记不记得，而是**三条不同性质的信息混在一处，互相污染**。于是我们把这三种信息拆成三条独立的轨，各自闭环（图 1）。

- **轨道一 · WBS 任务轨（该做什么）**：拆步骤、标负责人、定依赖，跟着派活走。它回答"这一步该谁做、依赖谁"。它的失真形态是——只记了做什么，没记谁负责，于是出了岔找不到手。
- **轨道二 · Issue 问题轨（出什么问题）**：新故障当场入轨，且必须带 `regressionOf` 关联，链回前序问题。它回答"这个错是不是又一次踩了同一个坑"。它的失真形态是——问题被口头记住，七天之后和"又一次谷底"认不出来。
- **轨道三 · 测试复核轨（做对没有）**：把结果分型记录——编译失败 / 同一测试仍败 / 引入新失败 / 超时。它回答"到底算不算做对了"。它的失真形态是——只标 PASS/FAIL，结果是失败的根因分析没人重做。

三轨分开追，意义在于**一条结论能同时被三种目光打量**：它怎么来的（WBS）、出了什么岔（Issue）、凭什么说做对（Test）。这就是"判断结算点"——三条账在这里对齐，任何一步都能复核。

三条轨不是抽象概念，落成账本以后是三种字段完全不同的行。`[内部项目实测]` 里，任意一条交付都会留下三行各自闭环的记录，哪怕只是几句话：

```text
# WBS 轨：该做什么
W-2042  task=重构路由层  owner=Agent-EXEC-7  dep=W-2039  state=派发已确认

# Issue 轨：出了什么问题
I-1042  type=runtime  severity=high  regressionOf=I-1031  link=roundtrip  state=已验证关闭

# Test 轨：做对没有
T-0331  target=W-2042  verdict=fail  class=同一测试仍败  root=未重做回归分析  ts=2025-06-11 14:32
```

这三行的威力在"互相咬合"：WBS 行说"谁该做"，Issue 行用 `regressionOf` 链回"这是不是又一次踩同一个坑"，Test 行用四型分类（编译失败 / 同一测试仍败 / 引入新失败 / 超时）逼出"到底算不算做对"。缺了任何一列，三条账就接不上，"判断结算点"就塌成三处孤岛。

## 三、三权分立：复核的手必须不同

三轨是"账分开追"，三权是"手必须分开"。判断里最容易犯的隐蔽错误，是**自己验证自己**。模型给的答案，让它自己说"对不对"，它永远倾向"对"——因为打分和产出共用同一套隐藏偏好。这跟一个人写完代码自己签字验收是同一件事，代码没问题时你好我好，代码有问题时你永远发现不了。

破解的办法是**三权分立**（图 2）：报告人（R）只负责如实上报"哪里不对"，不负责改；修复人（F）只负责消除根因，不接受"可能没问题"的糊话；验证人（V）只负责用可复现的基准裁断，不参与修复。

这里面藏着一个常被忽略的关键——**同一双手也要时间隔离**。现实里你未必有三个人，常常是同一个人（或同一个 Agent 体系）既要报告又要修复又要验证。我们踩过的坑是：修完立刻自验，几乎 100% 通过；隔 30 分钟后回头复验，发现率直接翻倍。原因很简单：刚修完，"我以为我修好"的自我说服还热着。**时间本身就是最便宜的那第三双手。** 让验证和修复之间隔开一段，等于把"验证人"的身份从"修复人"手上剥下来，哪怕它们是同一个心智。

## 四、一次"只有分工、没有三权"的返工

这条纪律不是一个凭空的想法，是我用一次返工换来的。

早期我把三层分工搭得很漂亮，但验证环节偷了懒——让执行层在交付时顺带自评"通过"。结果遇到一次典型的隐蔽错：一个看似合理的方案，执行层自评"逻辑自洽、约束满足"，提交上线。真正的缺陷直到线上才暴露，而且因为"自己验自己"，问责时没有任何第三方证据能指出"这轮错在论证还是错在检验"。那一次之后我认真执行了一个改动：**任何交付，验证手必须独立于修复手；做不到人手独立，就把验证往后推半小时以上。** 

更麻烦的一种伪装是"分工的壳、三权的无"：三个角色的 prompt 写得清清楚楚，但整个流程还是同一个模型在底层，共享同一套温度、同一套偏好。这时候所谓的"报告、修复、验证"只是把同一个黑盒的叫法换了三次，**换名字不换手，等于没分立。** Multi-Agent 能立住，靠的是在三权之间放进真正的隔断——要么换对象，要么至少隔时间、隔约束。

AutoGen 的 GroupChat 就是个典型。它允许你定义很多个"assistant agent"围坐一桌聊天，你来我往，看起来热闹又分工明确。可你把流程拉到尽头看，GroupChat 的核心是一个共享的 `groupchat_manager`，所有 agent 的发言、投票、总结都经由同一个调度提示词驱动，底层的 `llm_config` 常常还是同一份。这带来一个隐蔽的问题：**当一个"验证 agent"说"这轮没问题"时，它和刚才产出结论的"执行 agent"共享同一套权重与偏好，那么这句"没问题"并没有引入一点点新的证据——它只是同一个判断给自己盖了个章。** `[内部项目实测]` 里，我们见过配置了十几个角色的 GroupChat，出问题时定位起来跟单 Agent 一样难，因为三权那三道隔断，在同一个底层心智里根本没有真实存在过。

同样地，"报告、修复、验证同一人"是最常见也最隐蔽的自毁方式。`[内部项目实测]` 里，有一次节奏太紧，我同意让同一个人一边修、一边验，理由是"他上下文最全"。他修完提交，验证那一刻自己也隐隐觉得"应该好了"，结果同一个回归三周后又冒出来。不是他粗心，而是"我自己修的，我当然希望它是对的"——这个念头本身就是最大的第三方漏洞。后来那条硬规则立起来之后，团队里再没人敢在验证步上偷时间：**人手不够就隔时间，时间也缺就把验证拆成独立模型、独立温度、独立约束，总之三权不能是同一个心智能量下的三种姿态。**

## 五、三权合该长在哪只手上，才不是空转的机器

三权分立的陷阱不止"手没分开"，还有一个更隐蔽的：**手分开了，回路却没有闭合。** 报告人如实报了、修复人认真修了、验证人严格裁了，可修完的结果没有回流成一条新规矩，Issue 轨道上的 `regressionOf` 也没把这次升级链回旧坑——那么三条账每轮都完整跑了一遍，系统却站在原地：同一个坑三个月后照旧踩，三权成了一段漂亮却空转的仪式。

Multi-Agent 要的不是"每轮都走完流程"，而是**每轮都让系统长高一点**。判据就是每转一圈，账本里必须新增至少一条此前没有的东西——一条被验证过的新不变量，一条链接了 `regressionOf` 的防复发规则。如果一轮跑完，Issue 只是关掉而没回流成规矩，那这次三权在账目上是平的，在心里上是空的。`[内部项目实测]` 里，我们把"回流入账"设为三权的第五项验收：**修复手交付的不只是一个结论，还要交付"这条修法已固化成哪条规则"；验证手裁的不是"这次对没对"，而是"这条规矩立没立得住"。** 否则三权分得再清楚，也只是多花了几倍 token 把同一个错误重新表演一遍。

所以三权真正合该长在哪只手上，答案不是"分开就行"，而是**分开是为了让"每一次修正都能编译成一条新规则"这件事有人负责。** 这也是它和单纯"人多力量大"的根本区别：三权的产出是一个不断生长的账本，不是一个每次归零的流程。

## 六、原理飞升：判断可管理 = 分工 × 三轨 × 三权

把三篇连起来，多 Agent 的骨架就完整了：

> **可沉降的判断 = 可切（分工）× 可查（三轨）× 可分（三权）。** 分工把黑盒切成一串环节，三轨把环节的来龙去脉记成三条可复核的账，三权让"复核"这件事落到真正不偏私的手上。三者缺一，判断就退回不可管理。

这套结构的本源，是三百年多血液凝结的政治哲学。孟德斯鸠在《论法的精神》里说得最狠：**"要防止滥用权力，就必须以权力约束权力。"**听起来是在谈国家政体，其实是所有复杂系统的通用公理——任何自治机构，只要把"裁判权"和"做某事的手"捏在同一个主体手里，就必然走向自我辩护、停止自我纠错。多 Agent 的本质，是用软件复刻了这套"以权制权"，把人类的制衡智慧搬进了机器协作的回路里。

诚实地讲，三权分立不是没有代价。它更慢、更费 token、偶尔显得迂腐。但代价买来的是一件单 Agent 永远买不到的东西——**出错时可以指认，指认后可以修正，修完后可以证明。** 判断第一次从"听它的"变成了"可审计的"。

这也给下一篇递了棒。《选型是求解》要处理的问题是：既然要多 Agent，那"选哪个模型、组什么样"该怎么决定？答案是——别靠直觉拼拼图，把选型当成一次**约束求解**。从"管得住"，到"选得对"，多 Agent 从治理走到工程的第一件正事。
