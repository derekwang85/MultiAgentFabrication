# 序章：很多 Agent，然后呢？

> 从"一群会干活的 Agent"到"一群需要被约束的共犯"
> 首发于腾讯云开发者社区 ｜ 作者：derekwang85（腾讯云 TVP / 架构师名人堂）

---

## 一、会干活的 Agent，怎么变成了一群共犯

过去两年，多 Agent 是最热、也最容易被过度承诺的方向。你让五个 Agent 一起去"完成一个需求"，它们真能给你交出代码、文档、甚至测试。

于是问题来了：**为什么交付越多，你越心慌？**

因为从一开始，多数人把"多 Agent"当成"把一个人换成一队人开工"。你雇了一队 AI，它们各有能力、各说各话，然后你发现自己**从写代码的人，变成了盯着一群人吵架的监工**。你花在"协调它们别跑偏、别互相覆盖、别都以为自己是对的"上的精力，比亲自写还多。

这种现象有一个准确的描述：**一群需要被约束的共犯**。它们彼此没有责任边界，没有可度量的产出承诺，没有谁对结果负责。表面热闹，实则无生产力。

这不是"Agent 不够聪明"的问题，是**设计问题**：多 Agent 不是招人，是把任务、责任与约束切清楚。

## 二、一个反直觉的答案：生产力要"编"出来

我先给结论，剧透这个系列的核心主张：

> **多 Agent 的生产力不在"编排得漂亮"，而在选型 / 调用 / 校验 / 自愈四条链路闭环、全部声明式且可自证。**

拆成两层看：

- **分工层**（怎么组织这群 Agent）——责任切分、路由、门禁、谁最终负责。
- **可信层**（怎么证明它真的有用）——选模型靠约束而不是拍脑袋、输出靠基准而非"看起来对"、宣称和事实对齐。

很多团队死在第二层。他们能把一群 Agent 组织得井井有条，却答不出三个问题：

1. 这个任务为什么交给这个模型 / Agent，而不是另一个？——靠拍脑袋，不可复现。
2. 它的输出凭什么可信？——靠"多模型都这么说"，可多数也可能是多数弱智。
3. 你怎么证明这套系统真的比单 Agent 高效？——没有基准对照，分是假分。

这三问，缺一不可。答得清，多 Agent 才叫生产力；答不清，它只是多了一队需要人盯的共犯。

## 三、真实的转折：SmartQuant 是怎么把"一群人"变成"一圈生产力"

这个系列不是纸上谈兵。真正的转折来自我自己的真实项目。

早期系统（TradeOMS）是多 Agent 的"混乱共犯期"：Agent 能干活，但要人盯，靠事故驱动修补。后来在 SmartQuant 里，我选择**主动、结构化地布局**——把多 Agent 从"一群开工的人"重构成"一个会自己咬合的圈"。

SmartQuant 的关键不是 Agent 数量，而是它把工艺放在下列几条脊梁上：

- **约束即配置**：模型端点不再是硬编码 if-else，而是声明式画像（能力 / 智能度 / 成本 / 速度 / 质量）。
- **选型是求解**：给任务选模型，是多维约束求解——严格过滤 → 渐进松弛 → 显式失败，而不是"预算 A 挂了用 B"的线性 fallback。
- **输出靠基准**：多模型加权共识交叉验证，且有条防"分母错觉"的纪律——没跑到的模型不算数，不能被缺席者稀释掉高分的确信。
- **宣称对齐事实**：文档说能做的事，要么接 CI 可跑，要么标"目标值"，绝不把想要的当已经能跑的。
- **把人也转进圈里**：人工在决策点介入（HITL 闸门），反馈流回进化段，而不是当看客。

这几个机制，是这个系列后续每一篇要展开的骨架。它们共同回答初始问题：**会干活的 Agent 之所以能变成生产力，是因为有人把选择、校验、自愈缝成了一个可自证、可回流的闭环。**
