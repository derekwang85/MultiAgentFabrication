> 本宪法是所有写作工作（人 + AI）开工前必须加载的工作依据。

> 继承自 AIHarnessMethodology 已验证的写作宪法，针对"多 Agent 生产力"主题与 derekcoding 回馈纪律做了定制。

## 第一章 · 项目身份

### 1.1 一句话定位

《MultiAgent Fabrication · 多 Agent 生产力编织》系列技术方法论——不讲"多 Agent 是什么、怎么用一个框架"，专讲"**多 Agent 如何真正形成生产力、并自我证明它形成了**"。以 derekcoding-framework methodology #19 约束求解框架 + SmartQuant 多 Agent 调度经验为母版，对照 GitHub 高分多 Agent 项目做方法论对比与经验升华，写出有自己特色的工程方法论。

### 1.2 品牌锚点

| 项 | 内容 |
|----|------|
| 主标题 | 多 Agent 生产力编织 |
| 英文品牌 | MultiAgent Fabrication |
| 双关含义 | fabrication = 生产制造 + 构建装配 |
| 核心命题 | 多 Agent 的生产力不在"编排得漂亮"，而在选型 / 调用 / 校验 / 自愈四条链路闭环、全部声明式且可自证 |
| 作者署名 | 王海涛 / derekwang85（腾讯云 TVP / 架构师名人堂） |
| 首发平台 | 腾讯云开发者社区 |
| 系列归宿 | 完成后并入《RefactoringSoftwareEngineering》体系，为其核心延伸 |

### 1.3 目标读者

**主读者**：技术负责人 / 架构师 / 资深工程师——要圈层影响力，不追泛流量。

**次读者**：正在搭多 Agent 系统、却苦于"事后要人盯"的工程团队。

**不服务**：找框架教程的初学者、找 prompt 模板的速食读者。

## 第二章 · 写作铁律

### 2.1 三条不写

1. **不写框架对接/接入教程**——Menu 级内容是社区红海。
2. **不写泛多 Agent 科普**——多 Agent 模式图谱，别人已写透。
3. **不引精确 GitHub star 数**——只用相对定位（调研环境曾出现 star 数据污染）。

### 2.2 一篇文章的配方（固定三段）

| 段 | 内容 | 占比 |
|----|------|------|
| 方法论 | 核心主张、机制、原理 | ~40% |
| 项目实证 | derekcoding #19 / derekinside / SmartQuant 的真实文件 / 数字 / 挫败 | ~40% |
| 可复制清单 | "第一天就能用"的检查清单 / 操作步骤 | ~20% |

> 方法与示例的证据链细节，须遵循 `constitution/allusion-isolation.md` 的引用隔离规则

且每篇结尾必须有一个 **derekcoding / derekinside 活注脚**——"这个机制在 derekcoding/derekinside 里长这样"，链具体文件不链 README。

### 2.3 行为底线（内化自编程十诫）

| 编码十诫 | 写作对应 |
|---------|---------|
| 先读再写 | 先读宪法 + 上一篇 + 本门 spec 再动笔 |
| 显式假设 | 每个论断标注依据——经验 / 实证 / 引用 |
| 涟漪必检 | 每篇完稿检查对其他篇、对 derekcoding 回馈的影响 |
| 手术刀式 | 每段有明确职责，不写凑字数段落 |
| 验证优先 | 每个实证都能指认到具体文件 |
| 单一职责 | 一篇只讲一个核心主张 |
| 不信回忆 | 引用项目事实查真实源码，不靠记忆 |
| 失败安全 | 论断留余地，不把单点经验吹成普适真理 |
| 经验回写 | 发现的缺口回写宪法 / 门禁 / spec 模板 |
| 三次即替换 | 同类问题反复出现，换方法而非硬扛 |

### 2.4 认知纪律

| 纪律 | 写作场景含义 |
|------|------------|
| 置信度标注 | 未核实数字 / 未公开素材标注"未经核实"或"内部项目" |
| 反谄媚 | 不写"毫无疑问""毋庸置疑"；用事实和逻辑说话 |
| Post-hoc 审计 | 完稿后自问：结论会不会因"已写完"而被我过度维护？ |
| 不堆概念 | 一个词讲清的不堆三个同义词 |

### 2.5 工程现实纪律（本系列特色）

多 Agent 方法论最容易犯的错是"把想要的当已经能跑的"。本系列规定：

- 描述任何"我们做到了"的机制，必须能指认到一个真实文件或一次真实运行，否则改写为"设计目标/规划"。
- 引用 GitHub 项目的方法论时，只陈述其公开文档中**明确声称**的能力，标注"官方宣称"，不替它脑补。
- 调研数据（star、模式、社区共识）与 derekcoding 的"基准对照机制"一致：给出对照组，不写孤立结论。

## 第三章 · 工程原则（写作版）

继承 AIHarness 九条，并针对本主题增补两条：

**原则 10：自证优先**——任何"形成生产力/变快/改善"的论断，必须有对照组或可复现证据，否则退回为假设。焊死 SmartQuant 审查报告"没有基准的分是假分"的信条。

**原则 11：多 Agent 有成本要如实算**——不回避多模型 / 多 Agent 的 token、延迟、编排复杂度。每篇在合适位置给出"什么时候不值得上多 Agent"的边界（对齐 method 19 原则 2：单模型够用就别上多模型）。

## 第四章 · 发布纪律

### 4.1 门禁前置

- 每篇发布前必须通过 G1-G5（`writing-harness/writing-gates.py`），门禁不过不发布。
- 评分严格 > 前序均值（`writing-harness/evaluate.py --next` 亮基准），并落实至少一个前序未用过的突破维度。
- 分数回写三处：scoreboard JSON / docs 评分表 / SERIES-PLAN。

### 4.2 事实核查

- 所有引用项目数字 / 文件名 / 代码片段，发布前由非写作者核查（评审与写作分离）。
- 引用外部信息必须有可追溯来源链接。

### 4.3 双语策略

- 中文主场首发（腾讯云），英文重写跟进（非翻译），口径统一为 `essay`。

## 第五章 · derekcoding / derekinside 暗线纪律

### 5.1 定位

derekcoding-framework 是本系列的**方法论母版**（#19 约束求解是骨架），SmartQuant 是**实证母版**（多层调度与审计是活样本），derekinside 是**实现样本**（多模型认知引擎落地）。本系列是它们的"外化写作"，不是介绍软文。

### 5.2 铺法

- 每篇方法论落点都可指认到 derekcoding 某个 methodology 或 SmartQuant 某个文件。
- 末尾活注脚链具体文件。
- 调研发现的方法论缺口，独立沉淀为对 derekcoding 的回馈（见第五章下）。

### 5.3 回馈 derekcoding 纪律

本系列的最终研究成果，以**独立文档**形式回馈 derekcoding-framework，落于 `feedback-to-derekcoding/`：

- 回馈内容必须是我们**从调研与实证中新提炼**、且 derekcoding 现有方法论未覆盖或可强化的部分（如多 Agent 调度模式、门禁与审计的量化指标）。
- 回馈文档给出**明确落点**：对应 derekcoding 哪个 methodology 文件、建议新增哪节 / 哪个新方法论文件。
- 不夸大：标注新增内容为"待 derekcoding 内化确认"，不替 derekcoding 拍板。

### 5.4 三条红线

1. **不夸大**——derekcoding / derekinside 没有的功能不写。
2. **不硬塞**——与主题无关的不用硬拉。
3. **类比要标注**——对应到具体方法论时，明确说是"建议/对应"，不冒充 derekcoding 自有术语。
